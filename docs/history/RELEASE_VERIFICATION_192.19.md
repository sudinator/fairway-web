# 192.19.260930 — Game offline recovery and manual-handicap posting

Status: CANDIDATE; local gates PASS. Baseline 192.18.260930. Production remains deferred. GitHub fresh-Supabase reconstruction and live staging/device validation have not been executed here.

## Confirmed failures and resulting behavior

G1: GameRoom used a DB-first gap-fill merge, so an offline 5→4 correction or deletion lost to an existing server score. Stats-only recovery did not count as changed/pending. Load also ignored upload errors/zero affected rows and acknowledged the local merge rather than confirmed server data. Cold reads did not seed a baseline for rows without backups.

Recovery now uses the last confirmed watermark as a three-way baseline across scores, putts, fairways, penalties and sand. Locally changed cells win, including null, zero and false; untouched local cells take remote changes. A successful read seeds only the fetched server row as confirmed, leaving the local merge pending. Failed reads preserve local storage and prior display/snapshot state. Legacy backups with no watermark conservatively fill gaps; corrections/deletions cannot be inferred from an unknown baseline.

Every actual write goes through the same role-aware, column-scoped writer. Direct updates must return a visible matching stored row; the void stats RPC is followed by a matching-row read. Returned errors, thrown requests, zero rows, mismatched stored values and denied gross edits remain pending. Per-row queues read the latest durable backup at execution time and acknowledge only the sent snapshot; a newer tap remains pending. Current marker ownership is read through refs, including a whole-game marker fallback. Lifecycle flush uses the current writer. Reconnect/foreground/poll/manual sync read current reset and ownership state before draining. A reset on this device stops admission and waits for its admitted row writes before the existing RPC; passive mirrors retain the original edit timestamp so pre-reset backups cannot acquire false freshness.

H1: latest posting definitions (0139) halved every nine-hole game handicap and omitted manual source/audit columns. Follow-up 0161 preserves the exact manual handicap and course_handicap_source/course_handicap_set_by/course_handicap_set_at on both game and tee-group insert/update/conflict paths. Derived nine-hole handicaps retain the prior halving rule. Rating halves for an exact nine, par is the selected-hole sum, slope is unchanged; 12/18-hole, date preservation, system completion stamps and excluded formats retain their existing contracts. Applying 0161 alone changes no historical records; repost uses the corrected contract.

## Release limits and remaining audit scope

This candidate implements G1/H1; it does not certify every audit bug fixed. Remaining: structural partial operations/game creation atomicity; club-admin handicap writes affecting zero rows; failed reads outside this GameRoom path; push retries; stale card/badge clearing. Pending-access approval and Member since remain deferred. Live staging evidence and all release gates are required before closing these findings. Historical edits already lost under the old recovery behavior cannot be reconstructed by this patch.

Inference from the existing reset RPC and direct update paths: a write already in flight on a different device can still race a server reset, because the current database contract does not require a reset version on each score write. This candidate fixes stale offline replay after a confirmed reconnect and orders same-device writes/reset; it does not establish a cross-device transaction guarantee. Keep that concurrency gap on the structural-operations audit list; do not clear production on these local tests.
